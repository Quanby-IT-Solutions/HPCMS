# User Flows

## Patient Case Management System (PCMS) – St. Luke's Medical Center (SLMC)

> Derived from [USER_STORIES.md](user-stories.md) and the PCMS Terms of Reference.
> Each flow lists the step-by-step interaction and the wireframe pages required.
> Roles align with the 6 seeded HPCMS accounts: **System Admin**, **Tenant Admin**, **Supervisor**, **Case Agent**, **Clinician**, **Patient**.

---

## Section A — User Management & Security

### A1. All Roles – Secure Login with MFA

**User Flow**

1. User navigates to the PCMS login URL.
2. User enters their registered email address and password on the Login Page.
3. System validates credentials; if invalid, displays an inline error and increments the failed-attempt counter.
4. If credentials are valid, system checks whether MFA is required for the user's role.
5. System sends a one-time code via the user's registered MFA method (SMS, authenticator app, or email).
6. User is redirected to the MFA Verification Page and enters the one-time code.
7. System validates the code within its expiry window.
8. If the code is correct, system creates an authenticated session and records the login event (timestamp, IP address, user agent).
9. User is redirected to their role-appropriate home dashboard.

**Wireframe Pages**

- **Login Page** (email/password fields, "Forgot password?" link, SLMC branding)
- **MFA Verification Page** (one-time code entry field, resend code link, expiry countdown)
- **Role Home Dashboard** (landing page scoped to the authenticated user's role)

---

### A2. System Admin – Create User & Assign Role

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to User Management Page via the admin sidebar.
3. Clicks "Add New User" to open the Account Provisioning Form.
4. Enters user details: full name, email address, job title, and department.
5. Selects one or more facility tenants to assign to the user.
6. Selects the system role from the role dropdown (System Admin, Tenant Admin, Supervisor, Case Agent, Clinician, Patient).
7. Reviews the permission summary generated by the selected role.
8. Clicks "Create User"; system sends an activation email to the new user.
9. New user record appears in the User Management Page with status "Pending Activation".
10. System Admin can view the new user's profile and change history on the User Profile Page.

**Wireframe Pages**

- **User Management Page** (searchable user list with status badges, "Add New User" button)
- **Account Provisioning Form** (name, email, department, tenant assignment, role selector, permission summary)
- **User Profile Page** (user details, role, tenant assignments, account status, change history log)

---

### A3. System Admin – Deactivate / Deprovision User Account

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to User Management Page.
3. Searches for the target user by name or email.
4. Opens the User Profile Page for the target account.
5. Clicks "Deactivate Account" and selects the reason (e.g., employment termination, role change, security incident).
6. System displays a confirmation modal listing any open cases or active sessions for that user.
7. System Admin confirms deactivation.
8. System immediately terminates all active sessions for that user, sets account status to "Inactive", and logs the deprovisioning event with timestamp and actor.
9. User appears in the deactivated users filter on the User Management Page.
10. System Admin optionally reassigns the user's open cases before completing the flow.

**Wireframe Pages**

- **User Management Page** (user list with active/inactive filter, search bar)
- **User Profile Page** (account status, deactivate button, open case count, active session indicator)
- **Deactivation Confirmation Modal** (reason selector, affected sessions/cases summary, confirm/cancel)

---

### A4. Any Role – Self-Service Password Reset

**User Flow**

1. User navigates to the Login Page.
2. Clicks "Forgot password?" link.
3. User is taken to the Password Reset Page and enters their registered email address.
4. System sends a time-limited password reset link to the provided email.
5. User clicks the link and is taken to the Identity Verification Page.
6. System requires the user to verify identity via a secondary factor (registered MFA method or security question).
7. After successful verification, user is presented with the New Password Form.
8. User enters and confirms a new password meeting the system's complexity policy.
9. System validates and saves the new password, invalidates all existing sessions, and displays a success confirmation.
10. User is redirected to the Login Page to sign in with the new password.

**Wireframe Pages**

- **Login Page** (email/password fields, "Forgot password?" link)
- **Password Reset Page** (email entry field, submit button, "Return to login" link)
- **Identity Verification Page** (MFA code entry or security question prompt)
- **New Password Form** (new password field, confirm password field, policy hint text, submit button)

---

### A5. System Admin – Configure Session Timeout & Concurrent Session Policy

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to Security Settings Page via the admin sidebar.
3. Selects the "Session Management" sub-section.
4. Sets the idle session timeout duration (in minutes) for each role tier.
5. Sets the maximum number of concurrent sessions allowed per user account.
6. Toggles the "Force single session" option for high-privilege roles (System Admin, Tenant Admin).
7. Optionally enables a warning banner that appears N minutes before session expiry.
8. Clicks "Save Policy"; system applies the new settings and records the change in the audit log.
9. Reviews the Active Session Management Page to confirm no currently active sessions violate the new policy.

**Wireframe Pages**

- **Security Settings Page** (tabbed config: password policy, session policy, MFA policy)
- **Session Management Panel** (idle timeout fields per role, max concurrent sessions field, single-session toggle, warning banner config)
- **Active Session Management Page** (live table of active sessions: user, role, IP, last activity, terminate button)

---

### A6. System Admin – Configure Tenant-Aware Authorization

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to User Management Page.
3. Opens the Tenant Configuration Page.
4. Reviews the list of configured tenants (e.g., SLMC Quezon City, SLMC BGC).
5. Selects a user from the Tenant Assignment Panel.
6. Assigns the user to one or more tenants by checking the relevant facility checkboxes.
7. Sets cross-facility access level: "None", "Read-Only", or "Full" per tenant pairing.
8. Saves the tenant assignment; system validates and records the change.
9. Reviews the Access Control Page to confirm the user's effective permissions are scoped correctly to their assigned tenants.

**Wireframe Pages**

- **User Management Page** (user list, search, tenant filter)
- **Tenant Configuration Page** (list of tenants with edit controls, add tenant button)
- **Tenant Assignment Panel** (user-to-tenant mapping table, facility checkboxes, cross-facility access level selector)
- **Access Control Page** (effective permissions matrix: user × tenant × resource type)

## Section B — Patient Master & Patient 360

### B1. Supervisor – Register New Patient

**User Flow**

1. Supervisor completes Login (A1).
2. Navigates to the Patient Search Page to confirm the patient does not already exist (enter name, date of birth, contact number).
3. If no match is found, clicks "Register New Patient".
4. Patient Registration Form opens pre-filled with any search terms already entered.
5. Supervisor enters full demographic data: full name, date of birth, sex at birth, ethnicity, address, email, phone number, and emergency contact.
6. Enters or selects HMO coverage information if available.
7. Selects consent flags: data processing consent, communications consent, specific service consent categories.
8. Clicks "Save Patient"; system checks for potential duplicates before committing.
9. If a potential duplicate is detected, a Duplicate Detection Alert Modal appears for review (see B7).
10. If no duplicate, record is saved; Supervisor is redirected to the new Patient Profile Page.

**Wireframe Pages**

- **Patient Search Page** (multi-field search: name, DOB, MRN, contact; results table)
- **Patient Registration Form** (demographic fields, consent flag toggles, HMO info section)
- **Duplicate Detection Alert Modal** (matched record summary, "Use Existing" vs. "Create Anyway" actions)
- **Patient Profile Page** (demographics summary, MRN, consent status, enrolled programs, assigned devices, case history)

---

### B2. Case Agent – Search and Look Up Patient

**User Flow**

1. Case Agent completes Login (A1).
2. Navigates to the Patient Search Page from the main navigation or case creation context.
3. Enters one or more search identifiers: name, date of birth, MRN, contact number, or HMO card number.
4. Clicks "Search"; Patient Search Results Page displays matching records with name, DOB, MRN, and facility.
5. Reviews results and clicks the correct patient row.
6. Patient Profile Page opens showing demographics, active cases, consent status, and communication timeline summary.
7. Case Agent can navigate to the Patient 360 Timeline Page for full interaction history.
8. Case Agent can proceed to create or link a case from this context.

**Wireframe Pages**

- **Patient Search Page** (multi-identifier search form, search button, recent searches list)
- **Patient Search Results Page** (results table: name, DOB, MRN, facility, last case date; "Select" button per row)
- **Patient Profile Page** (demographics, MRN, consent flags, active cases widget, quick-access links)
- **Patient 360 Timeline Page** (chronological feed of all interactions, cases, communications across channels)

---

### B3. Supervisor – Update Patient Demographics

**User Flow**

1. Supervisor completes Login (A1).
2. Searches for and opens the target patient using Search and Look Up Patient (B2).
3. On the Patient Profile Page, clicks "Edit Demographics".
4. Edit Demographics Form opens pre-populated with current values.
5. Supervisor modifies the relevant fields (address, contact number, email, ethnicity, emergency contact, etc.).
6. Enters a reason for the change in the mandatory change-reason field.
7. Clicks "Save Changes"; system validates input and commits the update.
8. System records the change in the patient's audit history with actor identity and timestamp.
9. Supervisor is returned to the updated Patient Profile Page with a success notification.

**Wireframe Pages**

- **Patient Profile Page** (demographics summary panel with "Edit Demographics" button)
- **Edit Demographics Form** (editable demographic fields, change-reason field, save/cancel buttons)
- **Patient Audit History Panel** (chronological log of all record changes with actor and timestamp)

---

### B4. Supervisor – Link Patient MRN to Altera Sunrise

**User Flow**

1. Supervisor completes Login (A1).
2. Opens the target patient's Patient Profile Page via B2.
3. Locates the "EMR Linkage" section and clicks "Link MRN".
4. MRN Linking Form opens; Supervisor searches for the patient in Altera Sunrise by name, DOB, or partial MRN.
5. System queries the FHIR Patient resource from Altera Sunrise and returns matching results.
6. Supervisor selects the correct EMR patient record.
7. System maps the Altera Sunrise patient ID to the PCMS patient record and saves the linkage.
8. A FHIR data sync is triggered automatically to pull current demographics and clinical context.
9. Supervisor reviews the FHIR Sync Status Panel to confirm the sync completed successfully.
10. Patient Profile Page now displays the linked MRN and sync timestamp.

**Wireframe Pages**

- **Patient Profile Page** (EMR Linkage section showing current MRN and last sync time)
- **MRN Linking Form** (Altera Sunrise patient search, results list, "Link" button)
- **FHIR Sync Status Panel** (sync status badge, last sync timestamp, sync error log, "Trigger Manual Sync" button)

---

### B5. Supervisor – Record / Update Patient Consent Flags

**User Flow**

1. Supervisor completes Login (A1).
2. Opens the target patient's Patient Profile Page via B2.
3. Navigates to the Consent Management Panel on the patient's profile.
4. Reviews current consent flags and their effective dates.
5. Clicks "Update Consent" to open the Consent Recording Form.
6. Selects the consent category (data processing, communications, specific service type).
7. Sets the consent status (Granted / Withdrawn / Not Collected) and records the method of capture (written, verbal, electronic).
8. Saves the consent record; system timestamps the entry and records the staff member's identity.
9. Consent History Log is updated to reflect the new entry.
10. If consent is withdrawn, system immediately restricts affected communication and data-use actions for that patient.

**Wireframe Pages**

- **Patient Profile Page** (Consent Management Panel with current flags, "Update Consent" button)
- **Consent Recording Form** (category selector, status radio buttons, method of capture, notes field, save button)
- **Consent History Log** (chronological list of all consent changes: category, status, actor, timestamp, method)

---

### B6. Case Agent – View Patient 360 Communication Timeline

**User Flow**

1. Case Agent completes Login (A1).
2. Searches for and opens the target patient using B2.
3. Clicks "View Full Timeline" or the "360 Timeline" tab on the Patient Profile Page.
4. Patient 360 Timeline Page loads a chronological feed of all interactions.
5. Each timeline entry shows: channel icon (email, phone, portal chat, social media), date/time, case reference, agent name, and a summary snippet.
6. Case Agent applies channel, date range, or case type filters using the Timeline Filter Panel.
7. Case Agent clicks an individual entry to expand the full interaction detail inline or in a side drawer.
8. Case Agent can navigate directly to the linked case or communication record from the timeline entry.

**Wireframe Pages**

- **Patient 360 Timeline Page** (chronological interaction feed, channel icons, date/time stamps, case reference links)
- **Timeline Filter Panel** (channel checkboxes, date range picker, case type selector, agent filter)
- **Interaction Detail Drawer** (full message/call summary, linked case, agent, channel metadata, "Go to Case" button)

---

### B7. Case Agent – Detect and Merge Duplicate Patient Records

**User Flow**

1. Case Agent completes Login (A1).
2. During patient registration (B1) or patient search (B2), the system surfaces a Duplicate Detection Alert Modal when a new record closely matches an existing one (based on name, DOB, contact).
3. Case Agent reviews the side-by-side comparison of the suspected duplicate and the existing record.
4. If the records represent the same person, Case Agent clicks "Merge Records".
5. Merge Confirmation Page shows a field-level resolution table; Case Agent selects which field values to keep as the master.
6. Case Agent adds a merge reason note.
7. Confirms the merge; system combines case history, communication timeline, and consent flags onto the surviving record.
8. The superseded record is marked as merged (not deleted) and redirects to the master record.
9. System logs the merge event in the patient's audit history.

**Wireframe Pages**

- **Duplicate Detection Alert Modal** (side-by-side record comparison, "Use Existing", "Merge", "Create Anyway" actions)
- **Merge Confirmation Page** (field-level resolution table, master field selectors, merge reason field, confirm button)
- **Patient Profile Page** (post-merge view showing merged timeline and updated demographics)
- **Patient Audit History Panel** (merge event entry with actor and timestamp)

## Section C — Healthcare Case Management

### C1. Case Agent – Create New Healthcare Case

**User Flow**

1. Case Agent completes Login (A1).
2. Searches for and selects the patient using B2.
3. From the Patient Profile Page, clicks "New Case".
4. New Case Form opens pre-linked to the selected patient.
5. Selects the case type from the configured list (e.g., LOA Request, Billing Inquiry, Complaint, Care Coordination, Drug Program Enrollment).
6. Selects the source channel (email, phone, portal, social media, walk-in).
7. Sets the initial priority (Low, Normal, High, Urgent).
8. Optionally links an attending practitioner using the FHIR-backed Practitioner Lookup component.
9. Enters a case description / chief complaint in the free-text field.
10. Assigns the case to a team or leaves for supervisor routing.
11. Clicks "Submit Case"; system creates the case record and opens the Case Detail Page.
12. System logs the case creation event and notifies the assigned team.

**Wireframe Pages**

- **Patient Profile Page** ("New Case" button in the cases section)
- **New Case Form** (case type selector, source channel, priority, practitioner lookup, description field, team assignment)
- **Case Detail Page** (full case record: header info, status timeline, linked communications, action buttons)

---

### C2. Case Agent – View and Triage Case Queue Dashboard

**User Flow**

1. Case Agent completes Login (A1).
2. Is taken to or navigates to the Case Queue Dashboard.
3. Dashboard displays all open cases assigned to the agent or their team in a sortable table/card view.
4. Case Agent reviews columns: case ID, patient name, case type, priority badge, status, age (days open), and SLA indicator.
5. Applies filters via the Case Filter Panel: priority, case type, status, assigned agent, date range.
6. Sorts the queue by priority or SLA breach risk to identify most urgent items.
7. Clicks a case row to open the Case Detail Page for that case.
8. Optionally uses a "Quick Actions" context menu per row to update status or reassign without opening full detail.

**Wireframe Pages**

- **Case Queue Dashboard** (table/card view of open cases, column headers sortable, SLA countdown badges, priority color coding)
- **Case Filter Panel** (priority checkboxes, case type multi-select, status filter, agent filter, date range picker)
- **Case Detail Page** (full case record accessible from dashboard rows)

---

### C3. Supervisor – Assign and Route a Case

**User Flow**

1. Supervisor completes Login (A1).
2. Navigates to the Case Queue Dashboard.
3. Identifies an unassigned or misrouted case and opens its Case Detail Page.
4. Clicks "Assign / Route" in the Case Assignment Panel.
5. Selects the target team from the department/team dropdown.
6. Selects a specific agent from the agent list, which shows each agent's current open case count.
7. Optionally adds routing notes explaining the assignment rationale.
8. Clicks "Confirm Assignment"; system updates the case's assigned team and agent, timestamps the action, and sends a notification to the assignee.
9. Assignment event is recorded in the Case Status History Panel.

**Wireframe Pages**

- **Case Queue Dashboard** (full case list with unassigned filter)
- **Case Detail Page** (case header, status, communication history, assignment section)
- **Case Assignment Panel** (team dropdown, agent list with workload indicators, routing notes field, confirm button)
- **Case Status History Panel** (timestamped log of all status and assignment changes)

---

### C4. Supervisor – Escalate a Case

**User Flow**

1. Supervisor completes Login (A1).
2. Opens the target case via the Case Queue Dashboard or a direct link.
3. Reviews the Case Detail Page and identifies that escalation is warranted (SLA breach, complexity, patient complaint).
4. Clicks "Escalate Case" to open the Escalation Form.
5. Selects the escalation level (e.g., Senior Coordinator, Department Head, Incident Management).
6. Selects the escalation reason from the category list.
7. Enters a detailed escalation note.
8. Clicks "Submit Escalation"; system updates case status to "Escalated", re-routes to the target team, and notifies the escalation target.
9. Escalation event is appended to the Case Escalation History Panel with actor, timestamp, and notes.
10. SLA clock is updated to reflect escalation-level thresholds.

**Wireframe Pages**

- **Case Detail Page** (status banner, "Escalate Case" button, SLA timer)
- **Escalation Form** (escalation level selector, reason category, notes field, submit button)
- **Case Escalation History Panel** (log of all escalation events: level, reason, actor, timestamp)

---

### C5. Case Agent – Resolve and Close a Case

**User Flow**

1. Case Agent completes Login (A1).
2. Opens the target case from the Case Queue Dashboard.
3. Reviews the Case Detail Page to confirm all required actions are complete.
4. Clicks "Resolve Case" to open the Resolution Notes Form.
5. Enters resolution summary describing actions taken and outcome.
6. Selects the resolution category (e.g., Resolved – Patient Satisfied, Resolved – Escalated to Clinician, Closed – Duplicate).
7. Optionally attaches supporting documents or links related communications.
8. Clicks "Close Case"; system sets status to "Resolved", records the closure timestamp, and updates SLA metrics.
9. Patient receives an optional automated notification that their case has been closed.
10. Closed case appears in the Case Status History Panel and remains searchable but read-only for agents.

**Wireframe Pages**

- **Case Queue Dashboard** (in-progress case list with "Resolve" quick action)
- **Case Detail Page** (full case record, "Resolve Case" button visible when status is "In Progress" or "Pending Patient")
- **Resolution Notes Form** (resolution summary field, resolution category selector, attachment uploader, submit button)
- **Case Status History Panel** (full lifecycle log including resolved/closed events with timestamps)

---

### C6. System Admin – Configure Extendable Case Types

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to the Case Type Configuration Page via the admin settings menu.
3. Reviews the Case Type List Page showing all active and inactive case types.
4. Clicks "Add Case Type" to open the configuration form.
5. Enters the case type name, description, default priority, and SLA threshold.
6. Selects which teams or departments should handle this case type by default.
7. Configures required fields and optional fields for the New Case Form when this type is selected.
8. Sets the routing rule for auto-assignment (optional).
9. Clicks "Save"; the new case type appears immediately in the case creation dropdown.
10. Existing case types can be edited or archived from the Case Type List Page.

**Wireframe Pages**

- **Case Type Configuration Page** (form for creating or editing a case type: name, SLA, required fields, routing)
- **Case Type List Page** (table of all configured case types with active/inactive status, edit and archive actions)
- **New Case Form** (downstream consumer; shows the new case type in the type selector)

---

### C7. Supervisor – Link Related Cases Together

**User Flow**

1. Supervisor completes Login (A1).
2. Opens the primary case's Case Detail Page.
3. Scrolls to the Related Cases Panel and clicks "Link Case".
4. Case Search Page opens in a modal; Supervisor searches by case ID, patient name, or case type.
5. Selects one or more related cases from the search results.
6. Selects the relationship type (e.g., "Follow-up from", "Spawned from", "Duplicate of", "Part of Incident").
7. Clicks "Link"; the related cases appear in the Related Cases Panel with relationship labels and links.
8. The linked cases also display a reverse reference to the primary case in their own Related Cases Panels.
9. System logs the link creation event with actor and timestamp.

**Wireframe Pages**

- **Case Detail Page** (Related Cases Panel with "Link Case" button and list of linked cases)
- **Case Search Modal** (search fields: case ID, patient name, case type, date range; results table with select checkboxes)
- **Related Cases Panel** (list of linked cases showing case ID, type, status, relationship label, "Open Case" link)

## Section D — Omni-Channel Communication Inbox

### D1. Case Agent – Unified Inbox View and Channel Triage

**User Flow**

1. Case Agent completes Login (A1).
2. Navigates to the Unified Inbox Page from the main navigation.
3. Inbox displays all incoming communications across channels (email, phone log entries, portal chat, social media) in a single sorted feed.
4. Each item shows: channel icon, sender/patient name, subject or summary, received timestamp, and current status (New, In Progress, Linked to Case, Resolved).
5. Case Agent applies filters via the Communication Filter Panel: channel type, status, assigned agent, date range.
6. Sorts by recency, priority, or unanswered duration.
7. Clicks an item to open its detail view and begin triage.
8. From the detail view, Case Agent can create a new case, link to an existing case, or mark as resolved.

**Wireframe Pages**

- **Unified Inbox Page** (multi-channel message feed with channel icons, status badges, sort and filter controls)
- **Communication Filter Panel** (channel checkboxes, status filter, date range picker, agent assignment filter)
- **Inbox Item Detail View** (full message/log content, patient identity, channel metadata, action buttons: Create Case, Link to Case, Resolve)

---

### D2. Case Agent – Reply to Patient Email from Inbox

**User Flow**

1. Case Agent completes Login (A1).
2. Opens the Unified Inbox Page.
3. Selects an incoming patient email from the inbox feed.
4. Email Thread View opens showing the full conversation history.
5. Clicks "Reply" to open the Email Reply Composer.
6. Composes the reply using the rich-text editor; optionally uses a response template.
7. Attaches supporting documents if required.
8. Selects the case to link this reply to (or creates a new case).
9. Clicks "Send"; the reply is dispatched via the integrated email channel.
10. The sent reply is appended to the Email Thread View and logged to the patient's 360 timeline.

**Wireframe Pages**

- **Unified Inbox Page** (email items identified by email channel icon)
- **Email Thread View** (full email conversation chain with timestamps, sender names, read/unread indicators)
- **Email Reply Composer** (rich-text editor, template selector, attachment uploader, case link selector, send button)

### D5. Patient – Send a Secure Portal Chat Message

**User Flow**

1. Patient completes Patient Portal Login (F2).

**Wireframe Pages**

- **Patient Portal Chat Page** (chat thread view, message input field, send button, notification badge for new replies)
- **Back-Office Inbox Chat Thread** (chat messages from patient, reply input, agent name, case link selector)

### D7. Case Agent – Search and Filter Interaction History

**User Flow**

1. Case Agent completes Login (A1).
2. Navigates to the Unified Inbox Page and clicks "Search Interactions" or opens the Communication Search Page.

8. Exports the report for JCI accreditation documentation.

**Wireframe Pages**

- **Handoff Audit Report Page** (filter panel: date range, department, case type; report table with completeness flags; export button)
- **Case Transfer History Panel** (timeline of all assignment and team transfer events for a case with completeness indicators)
- **Audit Log Viewer Page** (accessible for cross-reference of individual handoff events)

## Section L — Multi-Tenancy & Facility Administration

### L1. System Admin – Provision a New Facility (Tenant Onboarding)

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to the Tenant Configuration Page and clicks "Add New Facility".
3. New Facility Setup Wizard opens.
4. Step 1 – Facility Identity: enters facility name, short code (e.g., "SLMC-BGC"), address, and contact information.
5. Step 2 – Default Settings: configures default case types, SLA thresholds, and notification templates for this facility.
6. Step 3 – Department Setup: adds the initial list of departments and care teams for the facility.
7. Step 4 – Initial User Provisioning: optionally creates the first Tenant Admin user for the new facility.
8. Step 5 – Review & Activate: reviews all settings and clicks "Activate Facility".
9. System creates the tenant partition, applies default configuration, and notifies the initial Tenant Admin.
10. The new facility appears in the tenant list on the Tenant Configuration Page.

**Wireframe Pages**

- **Tenant Configuration Page** (list of existing tenants with status, "Add New Facility" button)
- **New Facility Setup Wizard** (5-step wizard: Identity, Default Settings, Departments, Users, Review)
- **Facility Settings Page** (post-creation configuration page showing all facility settings and edit controls)
- **User Provisioning Page** (initial admin user creation within the wizard context)

---

### L2. System Admin – Assign User to Tenant(s)

**User Flow**

1. System Admin completes Login (A1).
2. Navigates to User Management Page and opens the target user's User Profile Page.
3. Clicks "Manage Tenant Access" in the Tenant Assignment Panel.
4. A tenant assignment modal displays all configured facilities with checkboxes.
5. System Admin checks the facilities the user should have access to.
6. For each assigned facility, sets the access level: Full Access, Read-Only, or No Access.
7. Optionally grants cross-facility access by enabling the "Cross-Facility" permission flag with a justification note.
8. Clicks "Save Assignments"; system updates the user's effective access scope.
9. Change is logged in the audit trail.
10. User's next session will reflect the updated tenant scope.

**Wireframe Pages**

- **User Management Page** (user list with tenant assignment indicator column)
- **User Profile Page** (Tenant Assignment Panel showing current tenant memberships)
- **Tenant Assignment Modal** (facility checklist with access level selectors, cross-facility permission toggle, save button)

---

### L3. Tenant Admin – Configure Facility-Specific Settings

**User Flow**

1. Tenant Admin completes Login (A1).
2. Navigates to the Facility Configuration Page for their assigned facility.
3. Reviews and edits SLA thresholds per case type (response time, resolution time in hours).
4. Navigates to the Notification Template Editor to customize automated notification messages for the facility (e.g., LOA submission confirmation, case closure notification).
5. Navigates to the Department Management Page to add, edit, or deactivate departments for the facility.
6. Reviews and updates default case routing rules specific to the facility.
7. Saves each section independently; all changes are logged in the audit trail.

**Wireframe Pages**

- **Facility Configuration Page** (tabbed sections: SLA Settings, Notifications, Departments, Routing Rules)
- **SLA Settings Panel** (table of case types with editable response time and resolution time fields)
- **Notification Template Editor** (template selector, rich-text editor, preview panel, save button)
- **Department Management Page** (department list with add, edit, and deactivate controls)

### L4. Tenant Admin – Define Shared Service Policies Across Tenants

**User Flow**

1. Tenant Admin completes Login (A1).
2. Navigates to the Shared Service Policy Page.
3. Reviews existing shared service policies (e.g., Central Claims Processing, Shared Care Program Management).
4. Clicks "Add Shared Policy" or edits an existing one.
5. Defines the policy: service name, participating tenants, access level (read, create, update), and justification.
6. Specifies which user roles at each facility are covered by the policy.
7. Saves the policy; it becomes active for the next authenticated session of covered users.
8. Shared policy is visible on the Cross-Tenant Permission Configuration page and the Facility Administration Dashboard.

**Wireframe Pages**

- **Shared Service Policy Page** (list of active shared policies with tenant participants, edit and delete actions)
- **Cross-Tenant Permission Configuration** (policy detail editor: service name, tenant checkboxes, role scopes, access level)
- **Facility Administration Dashboard** (summary of active shared policies alongside facility-specific settings)

### L5. Tenant Admin – Generate Cross-Facility Report with Tenant Filters

**User Flow**

1. Tenant Admin completes Login (A1).
2. Navigates to the Reporting Dashboard.
3. Clicks "New Report" to open the Cross-Facility Report Builder.
4. Selects report type (e.g., Case Volume by Facility, Claims Aging Cross-Facility, Consent Coverage by Tenant).
5. Sets date range and other report parameters.
6. In the Tenant Filter Panel, selects which facilities to include: both, QC only, or BGC only.
7. Clicks "Generate Report"; system queries data respecting the tenant scope of the requesting user.
8. Report renders with facility-separated columns or a combined view with a tenant label column.
9. Tenant Admin reviews and clicks "Export" to download as CSV or PDF.

**Wireframe Pages**

- **Reporting Dashboard** (report type cards, recent reports list, "New Report" button)
- **Cross-Facility Report Builder** (report type selector, date range, parameters, tenant filter panel, generate button)
- **Tenant Filter Panel** (facility checkboxes, combined vs. separated view toggle)
- **Report Export Page** (rendered report preview, format selector, download button)

### L6. Supervisor – Identify Cross-Facility Patient Context

**User Flow**

1. Supervisor completes Login (A1).
2. Searches for and opens a patient's Patient Profile Page via B2.
3. If the patient has records at multiple SLMC facilities, the Cross-Facility Patient Context Panel is displayed on the profile.
4. The panel shows: facilities where the patient has records, case counts per facility, and last interaction date per facility.
5. Supervisor reviews available cross-facility context (subject to their authorized access level as configured in L2 and L4).
6. If the Supervisor does not have cross-facility access, the panel shows facility names but hides case detail and displays a "Request Access" link.
7. Clicking "Request Access" opens a Multi-Tenant Access Request Form where the Supervisor provides a justification.
8. Request is sent to the System Admin for approval; Supervisor receives a notification once access is granted or denied.

**Wireframe Pages**

- **Patient Profile Page** (Cross-Facility Patient Context Panel visible for patients with multi-facility records)
- **Cross-Facility Patient Context Panel** (facility list with case counts, last interaction dates, "View Cases" links gated by access level)
- **Multi-Tenant Access Request Form** (justification field, facility and access level requested, submit button)
